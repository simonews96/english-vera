# pedagogy

## Topic
Pedagogical + memory design for an Italian A0->A2 adult learning travel English by voice with an AI tutor (6 months, ~45 min/day in 5-10 min sessions): SRS choice and conversational grading, CEFR micro-goals, correction technique, session loop, progress metrics, ASR-only pronunciation, data model.

## Summary
1. Use FSRS-6 via ts-fsrs 5.4.2 (MIT, zero deps, ~60 KB ESM, FSRS-6 default 21 weights baked in, request_retention 0.9) for BOTH phrases and recurring errors; a fixed ladder (1/3/7/14/30, reset on fail) is an acceptable zero-dependency fallback but has no calibration and no delay handling.
2. Benchmark on 9,999 Anki users / 350M reviews: FSRS-6 LogLoss 0.346 / RMSE(bins) 0.065 vs SM-2 0.722 / 0.203 and Anki-SM-2 0.513 / 0.142 (SM-2 is worse than the constant-average baseline 0.395 / 0.103). FSRS defaults need no per-user optimizer and handle delayed/opportunistic reviews, which is what conversational review produces.
3. Conversational grading must be strict: any failed first-attempt production = Again (Anki manual: pressing Hard when you forgot makes FSRS intervals "unreasonably high"); Hard = correct only after a clarification request or with heavy hesitation; Good = correct, unprompted, intelligible; Easy = spontaneous use in a new context. Binary Again/Good is explicitly supported.
4. Corrective feedback meta-analysis (Lyster & Saito 2010, 15 studies, n=827): recasts d=0.53, prompts d=0.83, explicit correction d=0.84 (between-group); prompts beat recasts within-group (1.14 vs 0.70). Design: recast first, then prompt self-repair, max 1-2 corrections per learner turn, L1 metalinguistic hint only for persistent rule-based errors.
5. Tutor L1 (Italian) fade: A0 weeks 1-4 up to 60-70% of tutor talk; A1 30-40%; A1+ 15-20%; A2 <=10-15% (Macaro's 10-15% threshold); learner triggers ("non ho capito", "più lento", "come si dice") always honored, never penalized in SRS.
6. Session (5-10 min): 1-2 min warm-up retrieval of 2-4 due items -> 5-6 min scenario with 3-4 beats -> 1.5 min closing in which the LEARNER produces three things (counts as a review) -> 30 s state summary. Equal/near-equal spacing beats expanding for long-term retention; retrieval must be followed by feedback.
7. Progress metrics instead of scores: phrases produced unaided, errors retired, scenarios completed without L1 help, learner talk share (target >=50% rising to 60%; classroom literature recommends STT 70-80%), help triggers/session trending down, can-do checklist.
8. ASR-only pronunciation = coarse intelligibility gate on KNOWN target phrases only (expected-text match, n-best, 2-of-3 attempts), biasing OFF during the check; literature: ASR word-string accuracy ~62% overall and ~42% on free L2 speech, not aligned enough with human listeners for fine feedback. Apple exposes a 0-1 confidence; Web Speech confidence availability unverified.
9. CEFR primary texts (Companion Volume, ALTE Can Do, self-assessment grid) were unreachable; A1/A2 travel can-dos below are reconstructed from ALTE snippets + memory and marked likely; verify wording before shipping.
10. Critical dependencies: FSRS defaults generalize; FSRS tolerates delay; Hard-for-forgotten corrupts scheduling.

## Recommendations
- SRS engine: adopt ts-fsrs 5.4.2 (FSRS-6) with fsrs({ request_retention: 0.9, maximum_interval: 180, enable_fuzz: true, enable_short_term: true, learning_steps: ['2m','8m'], relearning_steps: ['5m'] }). The two learning steps map to 'use it again later in the scenario' and 'produce it in the closing retrieval'; a new chunk that survives both graduates to a 1-3 day interval. maximum_interval 180 keeps every item observable within the 6-month program. Store params via generatorParameters() so they can change without migrating cards. Pin to 5.x; 6.0.0 (beta.12) removes elapsed_days.
- Two item types, one scheduler: (a) phrase/chunk cards keyed by the English chunk (test = produce it when the situation calls for it); (b) error cards keyed by target form in an obligatory context (test = next obligatory context, e.g. 'I am 30' when age comes up). Both use FSRS; error cards additionally track recurrence_count and consecutive_correct; retire an error when state=Review AND stability >= 30 days AND consecutive_correct >= 3 with zero recurrences in the last 5 opportunities; retired errors move to passive monitoring (reactivate on recurrence with forget(card, now, false)).
- Grading rule from the conversational signal (the tutor model emits one label per targeted item per turn, the app maps it): FAILED (not attempted, wrong, needed recast/translation, tutor supplied the form) -> Again; SELF_REPAIRED_AFTER_CLARIFICATION (correct after a clarification request or repetition prompt only, no form given) -> Hard; SELF_REPAIRED_AFTER_HINT (needed a metalinguistic hint) -> Again; PRODUCED (correct, unprompted, intelligible, pauses allowed) -> Good; SPONTANEOUS (used unasked in a new context, fluent) -> Easy, capped at 1 Easy per item per week. NOT_OBSERVED -> no review logged (FSRS tolerates the delay). Never let a failed first attempt become Hard.
- Review selection inside conversation: at session start compute R = scheduler.get_retrievability(card, now, false) for all cards; due set = cards with R < request_retention or due <= now; pick 2-4 for the warm-up by lowest R, and tag up to 3 more that fit today's scenario domain so the tutor can engineer natural opportunities ('ask for the Wi-Fi password' beat exists because that chunk is due). Hard cap 6 targeted items per session; if the Again rate in the last 3 sessions exceeds 30%, introduce no new chunks until it falls below 20% (Anki's 5-20% Again band is the healthy range).
- Fallback scheduler if ts-fsrs is rejected: 5-box ladder with calendar intervals 1, 3, 7, 14, 30 days (box index per item); Good/Easy promotes one box, Again demotes to box 1, Hard stays in box; same grading labels. Accept that it cannot estimate recall probability, cannot prioritize by R, and treats a 3-week gap like an on-time review; SM-2 is not worth implementing (worse-calibrated than a constant baseline on the benchmark and no better pedagogically than the ladder).
- Correction protocol per learner turn: (1) if the message is intelligible and the error is not today's target and not an active error card, let it pass (max 1-2 corrections per turn, prioritized: active error card > today's micro-goal form > global-intelligibility error); (2) first move is a recast embedded in a natural reply; (3) immediately create a primed-production opportunity: ask a question whose answer needs the corrected form in a NEW sentence (not 'repeat after me'); (4) if the learner still fails, use a prompt (elicitation: 'I ... ?', or repetition with rising intonation); (5) only on the second recurrence of a rule-based error give a one-line metalinguistic hint in Italian ('in inglese l'età si dice con to be: I am 30') and log an error card; lexical errors never get metalinguistic hints, just recast + reuse.
- L1 fading rule (share of tutor words in Italian, measured per session and shown to the tutor model as a target): A0 (weeks 1-4) <= 65% Italian, English for every target chunk and all scenario lines; A1 (weeks 5-12) <= 40%; A1+ (months 4-5) <= 20%; A2 (month 6) <= 12%. Level promotion is evidence-based, not calendar-based: promote when >= 80% of the level's micro-goals have a scenario completed unaided and the 14-day Again rate < 20%. Triggers always honored and never graded: 'non ho capito' / 'I don't understand' -> repeat the same English line slower and shorter, then Italian gloss if a second trigger follows; 'più lento' -> persist slow mode for the rest of the session; 'come si dice X' -> give the English chunk, ask the learner to use it immediately, create a chunk card with source=learner_asked. Two consecutive failures on the same beat -> Italian scaffold once, then back to English.
- Session loop (5-10 min, one scenario per session): 0) load learner state card; greet in 1 line. 1) WARM-UP 1-2 min: 2-4 due items as mini-questions, each graded, no teaching. 2) SCENARIO 5-6 min: 3-4 beats with a success criterion each (e.g. beat 'order': learner produces 'Can I have ... please' + a quantity); tutor lines <= 2 sentences; learner talk share target >= 50%. 3) CLOSING 1-1.5 min: 'Tell me three things you can say now' -- the learner produces them (free recall, Italian cue only after 5 s silence), each graded as a review; then the tutor states the one error to watch. 4) STATE WRITE 30 s: app updates cards, scenario checkpoint, and a 3-line session summary. Daily pattern for 45 min: 4-6 sessions, at most 2 new micro-goal sessions per day, the rest review/variant runs of earlier scenarios.
- Re-entry after interruption: persist a scenario checkpoint after every learner turn (scenario_id, beat_index, last_tutor_line, pending_correction, items_targeted_so_far). If resumed within 2 h: resume at the same beat with a one-line recap in English ('We're at the hotel desk; you asked for the Wi-Fi') plus Italian gloss at A0; if > 2 h: start a fresh session with warm-up, then offer to finish the scenario from the checkpoint; unfinished beats are not graded.
- Learner state card injected into the system/user prompt (<= 400 tokens, regenerated by the app, not by the model): level + evidence line; this week's micro-goal and today's scenario beats; due items (<= 6: chunk, gloss, R, last rating); active errors (<= 3: wrong -> target, hint_it, recurrences); preferences (slow mode, L1 share target, persona); last session summary (3 lines); checkpoint if resuming; metrics line (learner talk share last 5 sessions, Again rate 14d). Keep full histories out of the prompt and retrievable by id (just-in-time), per Anthropic's context-engineering guidance; if using the Claude memory tool instead, mirror the same fields in /memories/learner.md and assume interruption.
- Progress surface (no scores): weekly 'can now do' list (micro-goals with >= 1 unaided scenario completion), phrases produced unaided this week (count of first-attempt Good/Easy on distinct chunks), errors retired, learner talk share trend, help triggers per session trend, and a re-run of an early scenario (week 1 content) every 4 weeks as visible evidence of growth. Never show R, stability, Again counts or streak penalties to the learner; keep a soft streak at most. Demotivation guards: if two sessions in a row have Again rate > 35% or learner talk share < 30%, next session is a 'win' session (replay of a mastered scenario with one new chunk).
- Pronunciation with a recognizer only: run an intelligibility check only on known target chunks with a constrained expected text; score = content-word match between transcript (or any n-best alternative) and the expected chunk, 2 successful attempts out of 3 = intelligible, then stop (no drilling beyond 3 attempts in a session). Disable recognizer biasing/contextual strings during the check (biasing inflates matches); use confidence only to break ties. Log pron_attempts/pron_intelligible per chunk and surface 'the recognizer understood you' rather than a pronunciation grade. Add a weekly minimal-pair spot check in neutral frames for known Italian-L1 issues (ship/sheep, /h/ in hotel/hungry, th in 'thank/three', final vowel epenthesis 'bus-a', word stress in 'hotel/reservation'), since LM context otherwise masks these. Do not attempt phoneme-level or stress feedback from the transcript.
- Data model (fields). profile: id, l1='it', level {code: A0|A1|A1+|A2, since, evidence}, goal='travel', trip {dates?, destinations?}, daily_budget_min=45, session_len_min=[5,10], l1_share_target, slow_mode, persona, request_retention=0.9, fsrs_params_json, correction_pref, known_pron_issues[], metrics {talk_share_5, again_rate_14d, help_triggers_avg}, created_at. phrase: id, text_en, gloss_it, micro_goal_id, domain, function, level, variants_en[], card {due, stability, difficulty, scheduled_days, learning_steps, reps, lapses, state, last_review}, review_log[] {review, rating, state, stability, difficulty, scheduled_days, context_session_id, signal_label}, source (taught|learner_asked|emergent), produced_unaided_count, spontaneous_count, pron {attempts, intelligible, - Validation to run early (weeks 1-2 of use): log the model's signal labels alongside transcripts and spot-check 50 turns for over-generous labelling (the single biggest risk is FAILED turns being labelled Hard/Good); check that NOT_OBSERVED stays below ~40% of targeted items per session, otherwise the scenario engineering is not creating opportunities; verify Again rate sits in 5-25%.

## Open questions
- CEFR Companion Volume 2020, the Council of Europe self-assessment grid and the ALTE Can Do PDF were unreachable in this session (rm.coe.int, coe.int, cambridgeenglish.org, alte.org, eaquals.org all blocked); the A1/A2 descriptor wording above is from memory/snippets and must be verified before Italian glosses are published.
- Web Speech API (browser) facts could not be verified (MDN, caniuse, WICG spec, developer.chrome.com, webkit.org blocked): whether SpeechRecognitionAlternative.confidence is populated in Safari/Chrome, maxAlternatives behaviour, on-device vs server recognition, and Firefox support. If the app is a PWA, confirm these on the target browsers before relying on n-best or confidence.
- Exact effect sizes in Li 2010 and the McDonough & Mackey 2006 finding (repetition of recasts not predictive, primed production predictive) are from memory; the recast-then-new-sentence rule rests on them.
- No experimental source prescribes L1 share by level or a 1-2 corrections-per-turn cap; both are heuristics anchored to Macaro's 10-15% threshold and the focused-feedback literature. Consider A/B logging of correction density vs Again rate and talk share.
- Student-talk-time targets (70-80%) are classroom norms, not optima for a one-to-one voice tutor; the RCT on talk-time feedback (LAK 2024) could not be read in full (effect sizes unknown).
- FSRS-7 (fractional intervals, same-day reviews) exists in the benchmark; ts-fsrs 5.4.2 implements FSRS-6 and 6.0.0 is still beta (beta.12) -- check whether 6.0.0 changes the forgetting curve or Card schema before it lands.
- Whether to log NOT_OBSERVED opportunities as 'Manual' (Rating 0) entries for analytics without affecting scheduling; ts-fsrs FSRSReview supports rating 0 = Manual.
- Microlearning/short-session meta-analyses and SDT sources on informational vs controlling feedback were not reachable; the 'no scores, can-do list' recommendation is grounded in general retrieval-practice and SDT literature, not a verified study.

### C2: FSRS handles delayed and irregular reviews gracefully: after a delayed successful review stability converges to an upper bound rather than growing linearly, and FSRS is 'much better at scheduling cards that have been reviewed with a delay' than SM-2.
  WHY: Conversational review is opportunistic: items come up days late or not at all. A Leitner/SM-2 scheme punishes or over-rewards late reviews; if FSRS did not tolerate delay, in-conversation review would require forced flashcard-style drills instead.
  VERDICT: confirmed
  EVIDENCE: VERIFIED (bounded gain): fsrs-rs v6.6.2 src/model_v6.rs (commit 4bc0a09, 2026-10-01; the exact crate version pinned in ankitects/anki Cargo.lock) implements FSRS-6 stability_after_success_scalar = s*(e^w8*(11-d)*s^-w9*(e^{(1-r)*w10}-1)*hard_penalty*easy_bonus+1).clamp(S_MIN,S_MAX). Only r (retrievability, in (0,1]) carries the delay, so the factor is capped at e^{w10}-1 (default w10=0.796 -> ~1.22, vs ~0.083 at r=0.9): stability converges to a parameter-dependent upper limit as delay->inf. Same formula verified in py-fsrs scheduler.py (FSRS-6, 21 params). FSRS-7 (34 params, new in fsrs-rs, src/model_v7.rs stability_for_set_scalar) keeps the same saturating (e^{(1-r)*w}-1) term; its _delta_t argument is unused. VERIFIED (wording): awesome-fsrs wiki The-Algorithm (last edited 2026-07-28) says verbatim "instead of increasing linearly with the delay like the SM-2/Anki algorithm, the subsequent stability converges to an upper limit, which depends on your FSRS parameters" -- but only in the FSRS v4 and v3 sections (lines ~200, ~292); FSRS-6 section lists only deltas. VERIFIED (SM-2 contrast): ankitects/anki rslib/src/scheduler/states/review.rs legacy scheduler: good=(current_interval+days_late/2)*ease_factor, easy=(current_interval+days_late)*ease_factor*easy_multiplier (hard ignores days_late) -> linear in lateness. VERIFIED (quote origin): "FSRS is also much better at scheduling cards that have been reviewed with a delay, for example, if the user took a break..." is from awesome-fsrs wiki ABC-of-FSRS (last edited 2026-03-18), same author group. LIKELY (overall superiority, not delay-specific): srs-benchmark README rev f0cc681 (2025-06-06, 9,999 users): unweighted log loss FSRS-6 0.3214 vs Anki-SM-2 0.490 / SM-2 0.547; "FSRS-6-recency has a 99.6% superiority over Anki's variant of SM-2" with caveat "SM-2 wasn't designed to predict probabilities"; SM-2 rows removed from README after Sept 2025; no delay-stratified metric exists. Anki manual deck-options.md (main) contains no delay-specific FSRS claim.
  CORRECTION: Nuance, not refutation: (1) The bounded-growth statement is mathematically true for every FSRS version v3 through FSRS-7 (verified in current code), but the sentence itself lives only in the v3/v4 wiki sections. (2) "Much better than SM-2 at delayed cards" is the FSRS authors' qualitative claim; independent benchmarks show FSRS-6 beats SM-2/Anki-SM-2 on overall calibration but nothing stratified by delay. (3) For the design: FSRS-6 rounds elapsed time to whole days and routes same-day repeats (delta_t==0) through a short-term formula that ignores R, so multiple 5-10 min sessions on one day are not 'delay-graded'; FSRS-7 (fractional intervals, fast/slow stability) addresses this but is not yet confirmed enabled in Anki. (4) A very late success still gets a sizeable (up to ~15x the on-time increment with defaults) but capped boost; the failure path also uses a bounded e^{(1-r)*w14} term, so late failures are not punished extra.

### C3: Rating a forgotten item as Hard instead of Again breaks FSRS scheduling: 'If you press Hard when you have failed to recall the information, all intervals will be unreasonably high'; binary Again/Good use is explicitly acceptable.
  WHY: The whole mapping from a tutor's conversational success signal to FSRS ratings hinges on this: any failed first attempt (including self-repair after a hint) must be Again, and the design can safely collapse to Again/Good if the model's Hard/Easy judgments prove unreliable.
  VERDICT: confirmed
  EVIDENCE: VERIFIED (read 2026-10-02):
1) Anki manual deck-options.md @main (line introduced 2024-10-12, commit c78ee6d, still present): "FSRS can adapt to almost any habit, except for one: pressing "Hard" instead of "Again" when you forget the information. When you press "Hard", FSRS assumes you have recalled the information correctly (though with hesitation and a lot of mental effort). If you press "Hard" when you have failed to recall the information, all intervals will be unreasonably high."
2) Anki manual studying.md @main (line from 2024-11-19, commit 25c7494): "If you find it hard to use four answer buttons, you can also use only **Again** and **Good** buttons. Use **Again** for incorrect answers and use **Good** for correct answers." Button defs: Again = "incorrect or when you couldn't recall"; Hard = "correct, but you had doubts about it or it took a long time to recall". NOTE: this two-button sentence is general Anki guidance, not inside the FSRS section.
3) Independent: awesome-fsrs wiki The-Algorithm (wiki last commit 2026-07-28; FSRS-6 section): "The new stability after a successful review (the user pressed "Hard", "Good" or "Easy")" vs "The stability after forgetting (i.e., post-lapse stability)" / "(the user pressed "Again")"; "The value of SInc is always greater than or equal to 1 if the review was successful"; same-day: "we should ensure that SInc >= 1 when G >= 2".
4) Independent: fsrs-rs crate v6.6.2, src/model_v6.rs (repo HEAD 2026-10-01): next_state_scalar: `else if rating == 1 { stability_after_failure_scalar } else { stability_after_success_scalar(..., rating) }`; `hard_penalty = if rating == 2 { w[15] } else { 1.0 }`; same-day (delta_t==0): `if rating >= 2 { sinc.max(1.0) }`. So Hard is a pass with a multiplicative growth penalty; it NEVER lowers stability (long-term or same-day); only Again hits the post-lapse formula. model_v7.rs (FSRS-7 in progress) keeps `if rating > 1 { new_s_success } else { pls }`.
5) Independent: py-fsrs README: "Rating.Again (==1) forgot the card / Rating.Hard (==2) remembered the card with serious difficulty".
NUANCES: (a) Mechanistic restatement: Hard != lapse; it still raises Difficulty and applies hard_penalty, but stability is monotone non-decreasing, so a forgotten item rated Hard gets an interval >= its previous one. (b) Binary Again/Good is safe at the algorithm level: Good (3) always takes the success path with hard_penalty=easy_bonus=1, so w15/w16 simply never apply (likely: optimizer can't fit them but they are unused). (c) The claim's corollary "self-repair after a hint must be Again" is the researcher's inference; no source addresses hints. Consistent with studying.md's "be strict... if it would fail in real life, mark it as failed" but not explicit.
