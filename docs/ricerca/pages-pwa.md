# pages-pwa

## Topic
Vite + TypeScript voice app on GitHub Pages as installable PWA (Android Chrome, iPhone Safari, desktop Chrome/Edge), platform limits as of 2026-10

## Summary
Deploy: Settings > Pages > Build and deployment > Source = "GitHub Actions" (admin/maintainer only, manual); workflow = checkout + build + actions/configure-pages + actions/upload-pages-artifact (path ./dist) + actions/deploy-pages with permissions pages:write + id-token:write; *.github.io is HTTPS-only. Vite base must be '/<REPO>/' for project pages; vite-plugin-pwa derives manifest start_url/scope from base automatically.
PWA: Chromium install needs name|short_name, icons 192+512, start_url, display; no service worker required; beforeinstallprompt is Chromium-only. iOS installs only via Share > Add to Home Screen (Safari, and Chrome/Edge/Firefox since iOS 16.4); iOS 26 makes every added site open as a web app by default.
iPhone blockers for a voice app: (1) webkitSpeechRecognition works in a Safari tab but fails in Home Screen web apps (WebKit gates it on host-app Info.plist usage strings + SFSpeechRecognizer auth; reports 2021-2024, no fix in any Safari 16.4-26.2 release note). (2) Recognition is denied when page not visible and aborted on suspend; iOS suspends the page on lock/app switch, so no background listening. (3) speak()/audio need one user gesture first (WebKit code). (4) Screen Wake Lock works in Home Screen apps only from iOS 18.4. (5) No Vibration API on iOS at all. (6) Mic permission in standalone is reported to re-prompt per launch (older bugs; unverified on iOS 26).
Android Chrome PWA: SpeechRecognition (cloud, needs network), Wake Lock (Chrome 84+), Vibration, Media Session (Chrome Android 57+) and headset keys all work; persistent per-origin mic grant.
Desktop Chrome/Edge: install icon in address bar, beforeinstallprompt, "Allow on every visit" mic grant persists per origin (Chrome 116+ also offers one-time).
Fonts: self-host via @fontsource-variable/* (OFL allows bundling; keep license file, do not sell fonts alone), add woff2 to workbox globPatterns so the shell works offline.
Verdict: iPhone can be "good enough" (tap-to-talk with screen on, iOS 18.4+), not first class, unless STT on iOS is done via getUserMedia + your own/cloud recognizer instead of webkitSpeechRecognition.

## Recommendations
- Deploy: add .github/workflows/deploy.yml copied from Vite's static-deploy-github-pages.yaml (configure-pages v6, upload-pages-artifact v5 path ./dist, deploy-pages v5, permissions contents:read/pages:write/id-token:write, concurrency group 'pages'); tell the owner to set Settings > Pages > Source = GitHub Actions BEFORE the first run (configure-pages cannot enable it with GITHUB_TOKEN).
- Vite: base: '/<REPO>/'; in VitePWA set manifest.id '/<REPO>/' explicitly (plugin fills start_url and scope from base but not id); prefer hash routing or a single route so no 404.html trick is needed; if you need path routes, copy rafgraph 404.html with pathSegmentsToKeep = 1.
- PWA: registerType 'autoUpdate' + registerSW({ immediate: true }) is fine for a voice app with no forms, but persist session state to IndexedDB/localStorage first because autoUpdate reloads all windows; add the hourly r.update() check (GitHub Pages may cache sw.js ~10 min, unverified). Set workbox.globPatterns to ['**/*.{js,css,html,ico,png,svg,woff2}'] so fonts and icons precache; keep sw.js and index.html out of any long cache.
- Manifest/head for iOS: display 'standalone', theme_color, icons 192+512 (plus maskable for Android), apple-touch-icon 180x180 opaque, <meta name="apple-mobile-web-app-capable" content="yes">, <meta name="apple-mobile-web-app-status-bar-style" content="black-translucent"> only if you handle safe-area insets; do not expect background_color/orientation/display_override to work on iOS.
- Install UX: on Android/desktop hook beforeinstallprompt and show your own Install button; on iOS detect navigator.standalone === false and show a 'Share > Add to Home Screen' hint (no API exists); on iOS 26 every added site opens as a web app by default.
- STT strategy: feature-detect at runtime and on iOS standalone (navigator.standalone) do NOT rely on webkitSpeechRecognition; route to getUserMedia + MediaRecorder (iOS 18.4+ WebM, 26+ PCM/ALAC) + your own/cloud recognizer; keep webkitSpeechRecognition for Safari tab, Android Chrome and desktop. Handle 'not-allowed'/'service-not-allowed' by switching path automatically.
- Interaction model: tap-to-talk, never auto-start; start speechSynthesis and AudioContext inside the first tap (speak an empty utterance to unlock on iOS), acquire navigator.wakeLock in the same gesture and re-acquire on visibilitychange; document that iOS needs 18.4+ for the screen to stay on in the installed app and that nothing runs with the screen locked on iPhone.
- Headset/AirPods control: only feasible through Media Session while a media element is active; if you want stem-press to trigger listening, keep a looping silent <audio> playing during a session and bind play/pause handlers; test on iOS specifically (unverified) and expect the 30 s-paused lock-screen bug.
- Haptics: use navigator.vibrate only after feature detection; no haptic feedback is possible on iPhone web apps - use sound/visual cues instead.
- Mic permission: on iPhone PWA expect a prompt on each launch; ask for it inside the first 'Start' tap, not at load. On desktop Chrome/Edge and Android the per-origin 'Allow' persists.
- Fonts: npm i @fontsource-variable/<font>, import its CSS in main.ts, reference font-family '<Font> Variable'; keep the package's OFL.txt (or add LICENSE-fonts) in the repo; drop Google Fonts <link> tags so first offline load works.
- Target versions: iOS 18.4+ for a usable installed experience (Wake Lock), iOS 26.2+ to avoid the audio-element-after-reopen bug; Chrome 108+ (Android) / 112+ (desktop) for install; note Chrome Android lacks on-device recognition (processLocally).

### C2: On iOS, recognition and speech stop when the page is not visible: WebKit rejects recognition with 'not-allowed' when the view is not visible and aborts it on suspend; speech synthesis and WebRTC/Web Audio are suspended on lock/background; Screen Wake Lock in Home Screen web apps only works from iOS 18.4.
  WHY: Rules out hands-free/background listening on iPhone; the app must keep the screen on (Wake Lock) and sets the minimum iOS version (18.4) for a 'good enough' installed experience.
  VERDICT: confirmed
  EVIDENCE: Method note: WebSearch budget was exhausted and webkit.org, bugs.webkit.org, caniuse.com, developer.mozilla.org are blocked by the egress proxy, so evidence is from WebKit `main` source (raw.githubusercontent.com, read 2026-10-02), Apple's Safari release-notes JSON twins, and MDN browser-compat-data / caniuse data read from their GitHub raw JSON. No 2025-2026 StackOverflow/GitHub-issue reports could be checked.

1. SpeechRecognition rejected with not-allowed when view not visible — VERIFIED (independent of the claimant's source). Source/WebKit/UIProcess/SpeechRecognitionPermissionManager.cpp, `SpeechRecognitionPermissionManager::startNextRequest()`: after the speech-service, microphone and user-permission checks: `if (!page()->isViewVisible()) { completeCurrentRequest(WebCore::SpeechRecognitionError { WebCore::SpeechRecognitionErrorType::NotAllowed, "Page is not visible to user"_s }); return; }`. The check runs on every `start()` (SpeechRecognitionServer::start -> requestPermissionForRequest -> m_permissionChecker -> WebPageProxy::requestSpeechRecognitionPermission). JS sees `event.error === "not-allowed"`. Nuance: it is a start-time check; no WebKit code path was found that aborts an in-progress recognition purely because the page became hidden.

2. Aborted on suspend — VERIFIED. Source/WebCore/Modules/speech/SpeechRecognition.cpp: `void SpeechRecognition::suspend(ReasonForSuspension) { abortRecognition(); }` and `stop()` also calls `abortRecognition()` (+ stops capture source). Nuance: this is ActiveDOMObject suspension (BackForwardCache, page/process-swap suspension via `Page::suspendActiveDOMObjectsAndAnimations`, `Document::suspendScheduledTasks(ReasonForSuspension::PageWillBeSuspended)`). `Page::setIsVisibleInternal(false)` does NOT suspend ActiveDOMObjects (only scripted animations, device-motion, `visibilityStateChanged`). On iOS backgrounding the real stopper is process throttling: WebPageProxy::updateThrottleState drops the foreground assertion when `!isViewVisible()` unless the page `IsAudible` or `IsCapturingMedia`; an active SpeechRecognition does count as `HasActiveAudioCaptureDevice` (Document::updateIsPlayingMedia), so whether an already-running session survives a lock for some seconds is NOT settled by source (uncertain). Safari 26.0 (2025-09-15) also made SpeechRecognition secure-context only (151240414) — fine for GitHub Pages HTTPS.

3. Speech synthesis — code VERIFIED, lock behaviour UNCERTAIN. SpeechSynthesis.cpp: `SpeechSynthesis::suspend(ReasonForSuspension) { stopPlatformSpeech(); }` clears the queue and cancels the platform synthesizer. Synthesis runs in the UI process (WebPageProxy::speechSynthesisSpeak -> PlatformSpeechSynthesizerCocoa -> AVSpeechSynthesizer). No primary source found that ties screen lock/background to synthesis stopping; same ActiveDOMObject caveat as (2). Likely stops when the host app is suspended, but unverified. Related fixes: Safari 26.0 "pending utterances do not receive an error event when speech synthesis is cancelled" (148731039); Safari 27 (2026-09-14) `speechSynthesis.cancel()` removing later-queued utterances (46151521).

4. Web Audio suspended in background — VERIFIED with an important nuance. Source/WebCore/platform/audio/ios/MediaSessionManagerIOS.mm `resetRestrictions()`: `addRestriction(MediaType::WebAudio, BackgroundProcessPlaybackRestricted)`, Video: BackgroundProcessPlaybackRestricted, VideoAudio: ConcurrentPlaybackNotPermitted|BackgroundProcessPlaybackRestricted|SuspendedUnderLockPlaybackRestricted; plain `Audio` (HTMLMediaElement audio) and `MediaStreamCapturingAudio` have NO background restriction. MediaSessionManagerInterface::applicationDidEnterBackground(suspendedUnderLock) -> `beginInterruption(EnteringBackground)` -> PlatformMediaSession::beginInterruption -> `client().suspendPlayback()` UNLESS `shouldOverrideBackgroundPlaybackRestriction`. AudioContext.cpp: `AudioContext::shouldOverrideBackgroundPlaybackRestriction` returns true for EnteringBackground when `hasPlayBackAudioSession(document)` i.e. `navigator.audioSession.type` is `playback` or `play-and-record` (DOMAudioSession; Audio Session API in Safari 16.4+ per BCD api/AudioSession.json: safari 16.4, safari_ios mirror; chrome: false). So Web Audio can keep running under background/lock on iOS when the page sets `navigator.audioSession.type = "playback"` and audio is audible (foreground assertion "because we are playing audio"). Verified in source; not device-tested (likely in practice).

5. WebRTC/capture suspended in background — OVERBROAD. Document.cpp `updateCaptureSourceToPageMutedState`: on IOS_FAMILY a Microphone source gets `source.setIsInBackground(document.hidden())` (capture continues with a background flag) when `manageCaptureStatusBarInGPUProcessEnabled && !interruptAudioOnPageVisibilityChangeEnabled`; it is muted on hidden only if the `interruptAudioOnPageVisibilityChangeEnabled` setting is on; Camera is muted on hidden if `interruptVideoOnPageVisibilityChangeEnabled` (plus AVCaptureSessionWasInterruptedNotification handling in AVVideoCaptureSource.mm). WebPageProxy::updateThrottleState takes a foreground assertion "because media capture is active". Safari 27 release notes (2026-09-14): "Fixed the WebProcess AudioSession to remain active while microphone capture is live. (180505014)". Default values of those settings were not verified -> microphone/WebRTC audio continuing in background is likely, camera interruption likely.

6. Screen Wake Lock in Home Screen web apps from iOS 18.4 — VERIFIED by two independent sources. (a) Apple Safari 18.4 release notes JSON (Released March 31, 2025 — 18.4 (20621.1.15)), section Home Screen Web Apps > Resolved Issues: "Fixed Wake Lock API for Home Screen Web Apps. (108573133)"; Safari 16.4 notes: "Added support for the Screen Wake Lock API." (b) MDN browser-compat-data api/WakeLock.json: safari "16.4"; safari_ios [{version_added "18.4"}, {version_added "16.4", version_removed "18.4", partial_implementation true, notes "Does not work in standalone Home Screen Web Apps. See bug 254545 (webkit.org/b/254545#c32)"}]. caniuse wake-lock.json marks ios_saf 'y' from 16.4 with no PWA note (less precise). Safari 18.5–27.2 beta notes (grepped 2026-10-02) contain no later Wake Lock change. Behavioural nuance (WebCore/Modules/screen-wake-lock/WakeLockManager.cpp): `visibilityStateChanged()` releases all Screen locks when `visibilityState == Hidden` (spec "handling document loss of visibility"); the lock is a `SleepDisabler(Type::Display)`, so it only keeps the screen on while the app is in the foreground and cannot keep anything running in background.

Other 2025-2026 items found: Safari 26.0 "Added support for any website to become a web app on iOS or iPadOS (113034903)"; Safari 26.2 (2025-12-12) "Fixed an issue where an audio element failed to play when re-opening a Home Screen Web App (155336513)".

What would settle the remaining uncertainty: device test on iOS 18.4+/26 Home Screen web app: start recognition then lock screen (observe onerror/onend timing); speechSynthesis under lock; AudioContext with navigator.audioSession.type='playback' under lock; plus WebKit bug 254545 comments (blocked here).
  CORRECTION: Core claim holds; corrected/nuanced statement: (1) WebKit returns SpeechRecognition error 'not-allowed' ("Page is not visible to user") at start() time when the WKWebView is not visible — a per-start check, not a continuous one; an in-flight session is aborted on ActiveDOMObject suspension (bfcache/page suspension), and on iOS backgrounding the practical stopper is loss of the process foreground assertion; whether a running session survives a few seconds after lock is unverified. (2) Speech synthesis is cancelled on ActiveDOMObject suspend; stopping on lock is likely but not proven by a primary source. (3) Web Audio is interrupted on background/lock by default on iOS (WebAudio has BackgroundProcessPlaybackRestricted), BUT it continues if the page sets navigator.audioSession.type = 'playback' (or 'play-and-record') via the Audio Session API (Safari 16.4+) — AudioContext overrides the EnteringBackground interruption in that case. (4) 'WebRTC is suspended on background' is overbroad: on iOS microphone capture is not background-restricted (it gets a setIsInBackground flag, and active capture holds a foreground assertion; Safari 27 keeps the WebProcess AudioSession active while mic capture is live); camera capture is interrupted/muted. (5) Screen Wake Lock: API since Safari/iOS 16.4, but broken in standalone Home Screen web apps until iOS 18.4 (Mar 31 2025: "Fixed Wake Lock API for Home Screen Web Apps", 108573133; BCD bug 254545) — so 18.4 is the right minimum; the lock is released whenever the document becomes hidden, so it only keeps the screen on in the foreground. Design consequence unchanged: no background/hands-free listening on iPhone; keep screen awake via Wake Lock; iOS 18.4+ for the installed experience; consider navigator.audioSession.type='playback' if any audio must survive lock.

### C4: iOS Home Screen web apps are reported to re-prompt for microphone access on every launch (Safari tabs persist the grant), and no Apple release note since has announced persistence for Home Screen apps.
  WHY: If true, the iPhone experience can never be 'open and talk'; if iOS 26 now persists the grant, the iPhone UX moves much closer to first class. Needs a device test; this claim is only 'likely'.
  VERDICT: unresolved
  EVIDENCE: 1) The cited source does not support the claim (verified). ionic-team/capacitor#5580 ("iOS getUserMedia Permission Prompt every time after App reopen", opened 2022-04-23, closed 2022-11-10, 0 comments) is about a Capacitor iOS app, i.e. WKWebView, not a Home Screen web app: body says "In Safari it's fine but in a App with Capacitor is annoying", links bugs.webkit.org/215884 and a StackOverflow question about Safari 14.0.3. WKWebView prompting is the embedding app's job: Capacitor main now implements webView(_:requestMediaCapturePermissionFor:initiatedByFrame:type:decisionHandler:) and calls decisionHandler(.grant) (ios/Capacitor/Capacitor/WebViewDelegationHandler.swift). So this is a 2022 hybrid-app issue, since fixed on the Capacitor side, with no bearing on Home Screen web apps.

2) "No Apple release note since" is at least imprecise (verified text, platform uncertain). Safari 17.2 Release Notes, Web Apps > Resolved Issues: "Fixed an issue that repeatedly asks for camera access after relaunching a web app. (114110664)". The section mixes macOS Dock and iOS Home Screen items and this item names neither platform nor the microphone; no WebKit/WebKit commit references 114110664 (GitHub commit search), consistent with a fix in Apple's closed-source web-app host. Also Safari 18.4: "Fixed voice search to not re-prompt for camera or microphone permission after a page-initiated same origin navigation. (138122655)" and "Fixed MediaSession.setMicrophoneActive(true) prompting repeatedly if the microphone was muted by the user-agent once. (135941062)" (navigation/session level, not launch level). Safari 26.0: "Added support for any website to become a web app on iOS or iPadOS. (113034903)". Scanned Safari 16.4-18.6, 26.0-26.6 and 27 release notes (developer.apple.com JSON twins): no item states that Home Screen web apps persist camera/microphone grants across launches, and none states they do not.

3) Mechanism (verified from WebKit source, Source/WebKit/UIProcess/UserMediaPermissionRequestManagerProxy.cpp): WebKit skips the prompt only when the embedder's getUserMediaPermissionInfo returns PermissionState::Granted (request->setHasPersistentAccess()); WebKit's own grant cache m_grantedRequests is per-page in memory and is cleared by resetAccess()/clearCachedState(). Cross-launch persistence for Home Screen web apps therefore lives in Apple's closed-source web-app host, can differ from Safari, and can change without a WebKit-visible note.

4) Independent 2025-2026 evidence: no device-tested report either way found. Apple Developer Forums thread 788518 (Jun 2025, unanswered) reports Safari on iOS re-prompting for camera during SPA route navigation, not per launch, and does not say Home Screen mode. Thread 801146 (Sep 2025, iOS 26/26.6, iPhone 13-16) device-tests getUserMedia inside Home Screen web apps and reports 90-degree rotation and screen.orientation bugs but never mentions re-prompting. GitHub samsun076/MyMacros#94 (2026-08-15) states "iOS has a long-standing weakness where standalone web apps re-prompt for camera and microphone on every launch" as an untested hypothesis with no source. WWDC23 "What's new in web apps" describes camera/mic grants via system prompts and System Settings only for macOS web apps; it says nothing about iOS Home Screen permission persistence. caniuse stream.json note 4 ("Does not work in standalone running ('installed') PWAs") applies only to iOS 11.0-13.3; getUserMedia works in standalone from iOS 13.4 on.
