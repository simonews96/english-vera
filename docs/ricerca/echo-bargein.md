# echo-bargein

## Topic
Echo avoidance and barge-in for a browser-only voice assistant (SpeechRecognition in, speechSynthesis out) on desktop Chrome/Edge, Android Chrome, iOS Safari

## Summary
1. speechSynthesis audio never goes through the browser's audio pipeline: Chromium hands text to SAPI (Win), AVSpeechSynthesizer (mac), android.speech.tts (Android); WebKit uses AVSpeechSynthesizer. So any AEC whose reference is "audio Chrome plays" cannot cancel TTS.
2. Desktop Chrome default AEC = ChromeWide (reference = Chrome's own playback). A system-loopback reference exists (kSystemLoopbackAsAecReference, enabled by default, Windows 11 and macOS 14.2+ only) but is selected deterministically only with echoCancellation:"all" (runtime flag GetUserMediaEchoCancellationModes is stable); it adds 170 ms capture delay.
3. Desktop Chrome SpeechRecognition's own mic capture is raw (no AudioProcessing). AEC'd recognition needs recognition.start(track) (Chrome 135+, stable only Win/Mac/Linux; not Android, not Safari).
4. Android Chrome recognition runs in the Google app (own capture, beep, continuous has no effect); a getUserMedia AEC stream puts the phone in MODE_IN_COMMUNICATION (SCO/call volume) and may be silenced by Android's concurrent-capture policy.
5. iOS: SpeechRecognition and getUserMedia share one VoiceProcessingIO unit; any capture flips AVAudioSession to PlayAndRecord/VideoChat (HFP priority, speaker/earpiece routing, VPIO ducking of other audio); category change back is delayed 2 s. TTS at low volume/earpiece while capturing is widely reported through iOS 26.
6. cancel() never fires 'end': Chrome fires error 'canceled'/'interrupted' (possibly async later); WebKit fires error 'canceled' and before Safari 26 queued utterances got no event at all. Restart logic must key off end OR error.
7. Headset button: Media Session only works with an HTMLMediaElement that is playing (WebKit bestMediaElementForRemoteControls; Chrome treats <=5 s media as transient and AudioContext as ambient) -> silent looped >5 s <audio> carrier.
8. Silero via @ricky0123/vad-web: ISC/MIT, 2.3 MB model + 11.2 MB ORT wasm (non-JSEP), many open iPhone/Safari failures; energy VAD is the only safe baseline on iOS.
9. Strategy: strict half-duplex everywhere; tap-to-interrupt as universal barge-in; energy-VAD barge-in enabled only with headphones (no leak) or where AEC is system-wide (Win11/macOS 14.2+ with "all", iOS VPIO); neural VAD optional on desktop only.

## Recommendations
- Universal baseline (all platforms): strict half-duplex state machine. On speak(): recognition.abort() (not stop, to avoid a trailing result), set state=SPEAKING, speechSynthesis.cancel() then speak(). Re-arm recognition only from a single 'ttsDone' funnel fed by utterance.onend OR utterance.onerror (canceled/interrupted) OR a watchdog (expected duration from text length + 1.5 s), then wait a tail guard (120 ms wired/speaker, 300 ms when a Bluetooth output is suspected, plus 2 s on iOS if you also stopped a getUserMedia stream) before recognition.start(). Create a fresh SpeechRecognition object after every TTS on iOS.
- Barge-in for everyone: tap-to-interrupt (big on-screen button; also keyboard Space/Escape on desktop) — the only mechanism that works identically on iOS, Android and desktop. Treat VAD barge-in as a progressive enhancement that is enabled per capability probe, never assumed.
- Desktop Chrome/Edge (Win11 or macOS 14.2+): open one getUserMedia stream with {echoCancellation:{ideal:'all'}, noiseSuppression:true, autoGainControl:true}; read track.getCapabilities().echoCancellation — if it includes 'all', system-loopback AEC is available and TTS leak is largely removed, so (a) run recognition.start(track) on that same track (Chrome 135+, desktop only) and (b) run an energy VAD (AudioWorklet, 20 ms RMS, noise floor from first 300 ms after TTS onstart) on the same stream to detect barge-in during TTS. Expect ~170 ms extra capture latency. If 'all' is not offered (Linux, Win10, older macOS), fall back to strict half-duplex; with headphones you can still enable energy-VAD barge-in because there is no leak.
- Desktop: optional neural VAD only here (not on phones): vad-web 0.0.31 with silero_vad_v5 (2.3 MB) + ort.wasm non-JSEP build (11.2 MB wasm), lazy-loaded after first interaction; positiveSpeechThreshold ~0.6-0.8 and minSpeechFrames >= 3 to ignore TTS bleed; keep the energy VAD as the fallback when ORT fails to load.
- Android Chrome: keep recognition purely half-duplex (Google-app recognizer, raw capture, a start beep per session, no continuous). Do NOT hold a getUserMedia AEC stream open by default: it flips the phone into MODE_IN_COMMUNICATION (call volume, Bluetooth SCO narrowband) and Android's capture-sharing policy may silence either the recognizer or your stream. If you want VAD barge-in on Android, open the stream with {echoCancellation:false, noiseSuppression:false, autoGainControl:false} (no communication mode), enable the energy VAD only when a wired/BT headset output is detected or user opts in, and verify with the diagnostics below that recognition still returns results while the stream is open. Expect TTS to stop when the screen turns off or Chrome is backgrounded.
- iOS Safari: accept that any capture (recognition or VAD stream) puts the device in PlayAndRecord/VideoChat: TTS will be quieter, may go to the earpiece on iOS 17+, Bluetooth earbuds drop to HFP. Do the silent 'unlock' speak() inside the mic-button tap handler. Prefer NOT to open a second getUserMedia stream; if you do (energy VAD only — no onnxruntime on iOS), request echoCancellation:true so it shares the same VPIO unit as recognition, create the AudioContext after the stream (sample-rate mismatch), and rely on VPIO as the only leak suppressor. Never call speak() within ~2 s of stopping all capture if you expect speaker routing. Not available in home-screen web apps.
- Headset-button barge-in (all platforms): instantiate a looped silent <audio> (>5 s, e.g. 10 s of digital silence) started from the first tap; set navigator.mediaSession.setActionHandler for 'play','pause','stop' (and 'nexttrack' as a secondary 'interrupt') and map every one to interruptTts(); update playbackState to 'playing' while the assistant speaks. Without a playing media element Chrome treats the page as transient/ambient and WebKit has no element to bind remote controls to.
- Shake-to-interrupt is only worth it on iOS as an opt-in: DeviceMotionEvent.requestPermission() from a tap (iOS 14.5+), threshold on |a| delta over 150 ms; skip on desktop.
- Energy VAD design: AudioWorklet (Safari 14.1+/Chrome 66+) posting 20 ms RMS in dBFS; during the first 300 ms after utterance.onstart record maxLeak = max RMS (speaker leak level) and a running noise floor; barge-in = RMS > max(noiseFloor+12 dB, maxLeak+6 dB) for >= 150 ms (8 consecutive frames) while state=SPEAKING; if maxLeak is within 3 dB of the pre-TTS floor assume headphones and lower the margin to +9 dB over floor. Disable VAD barge-in automatically when maxLeak-noiseFloor > 20 dB (loud speaker, no AEC).
- Treat all output-side 'end' timing as approximate: never re-open the mic on the 'end' event alone; always add the tail guard and, on Bluetooth, consider AudioContext.outputLatency (if > 0.1 s assume BT) to lengthen it.

- Does Android Chrome engage Bluetooth SCO on Android 12+ without the BLUETOOTH_CONNECT permission (the Chromium code has a TODO for the prompt)?

## Critical claims + verdicts
### C1: speechSynthesis audio is produced by the OS TTS engine outside the browser's audio pipeline on every platform (Chromium SAPI/AVSpeechSynthesizer/android.speech.tts; WebKit AVSpeechSynthesizer), so a browser AEC whose reference is 'what Chrome plays' (Chrome-wide AEC, the default) cannot cancel it. Only system-wide references can: Chrome's loopback reference (Windows 11 / macOS 14.2+, selected deterministically by echoCancellation:'all'), Apple VPIO on iOS, Android platform AEC.
  WHY: Decides whether any full-duplex/VAD-during-TTS design is viable without headphones: on Linux, Windows 10, older macOS and Android (via the Google recognizer) it is not.
  VERDICT: confirmed
  EVIDENCE: All read 2026-10-02 from Chromium/WebKit main and Apple docs (WebSearch budget was exhausted, so no 2025-26 bug-tracker/StackOverflow reports were checked; everything below is primary-source code/docs).

A. TTS rendered outside the browser audio service [verified, 5 independent files]
- Windows content/browser/speech/tts_win.cc: CoCreateInstance(CLSID_SpVoice) -> ISpVoice::Speak(..., SPF_ASYNC); no media::AudioOutputStream/AudioRendererSink.
- Linux tts_linux.cc: libspeechd.so.2, spd_open("chrome","extension_api",...), spd_say(conn_, SPD_TEXT, ...) -> speech-dispatcher daemon renders.
- Android tts_android.cc + content/public/android/.../TtsPlatformImpl.java: android.speech.tts.TextToSpeech.speak(text, QUEUE_FLUSH, params, id) (only KEY_PARAM_VOLUME set) -> Android TTS service renders.
- macOS tts_mac.mm: [[AVSpeechSynthesizer alloc] init] ... speakUtterance:.
- WebKit Source/WebCore/platform/cocoa/PlatformSpeechSynthesizerCocoa.mm: WebSpeechSynthesisWrapper owns AVSpeechSynthesizer, [m_synthesizer speakUtterance:].

B. What each Chrome AEC reference contains [verified, media/base/media_switches.cc]
- kChromeWideEchoCancellation (ENABLED_BY_DEFAULT, BUILDFLAG CHROME_WIDE_ECHO_CANCELLATION): comment "mix and cancel all audio playback going to a specific output device in the audio service" => Chrome's own playback only; TTS from A is not in it.
- kSystemLoopbackAsAecReference (ENABLED_BY_DEFAULT, BUILDFLAG SYSTEM_LOOPBACK_AS_AEC_REFERENCE): "use system loopback audio as reference signal to be able to cancel echo from all audio processes and not only audio from Chrome". Params: forced_on=false, added_delay_ms=170 (capture is delayed 170 ms so the reference arrives first), num_filters=6.
- media/media_options.gni: chrome_wide_echo_cancellation_supported = is_win || is_mac || is_linux; system_loopback_as_aec_reference_supported = (is_win || is_mac) && chrome_wide_echo_cancellation_supported => Linux/Android/ChromeOS never have loopback AEC.
- IsSystemLoopbackAsAecReferenceEnabled(): macOS requires IsMacCatapSystemLoopbackCaptureSupported() = MacOSVersion() >= 14'02'00; Windows requires IsWindowsProcessLoopbackCaptureSupported() = base::win::GetVersion() >= Version::WIN11.
- Reference scope includes Chrome's own processes (so SAPI/AVSpeechSynthesizer output rendered in the browser process is in the reference): services/audio/loopback_reference_manager.cc opens kLoopbackAllDevicesId ("audio from all PIDs playing out audio"); media/audio/win/audio_low_latency_input_win.cc table: AllDevices -> TargetProcessId 4 (System), PROCESS_LOOPBACK_MODE_EXCLUDE_TARGET_PROCESS_TREE (only kLoopbackWithoutChromeId excludes Chrome's PID); media/audio/mac/catap_audio_input_stream.mm: exclude_chrome only for kLoopbackWithoutChromeId; kLoopbackAllDevicesId "capture all system audio regardless of the specific output device"; class is API_AVAILABLE(macos(14.2)).

C. How echoCancellation:'all' is resolved [verified]
- third_party/blink/renderer/modules/mediastream/media_stream_constraints_util_audio.cc: "all" -> EchoCancellationMode::kAll, "remote-only" -> kRemoteOnly, true -> kBrowserDecides, false -> kDisabled. kAll offered only if RuntimeEnabledFeatures::GetUserMediaEchoCancellationModesEnabled() (runtime_enabled_features.json5: status "stable") AND capture is DEVICE_AUDIO_CAPTURE (gUM mic) AND EchoCanceller::IsSystemWideAecAvailable(effects). kRemoteOnly excluded on Android/iOS. Ranking when fitness ties: kBrowserDecides(4) > kAll(3) > kRemoteOnly(2) > kDisabled(1); exact:'all' where unavailable => no candidate (OverconstrainedError).
- third_party/blink/renderer/platform/mediastream/media_stream_audio_processor_options.cc: IsSystemWideAecAvailable = (effects & ECHO_CANCELLER) || IsSystemLoopbackAsAecReferenceEnabled(). kAll -> GetSystemWideAec: kLoopbackBased if loopback enabled, else kPlatformProvided (CHECK platform effect). kBrowserDecides -> GetPreferredAec: kLoopbackBased only if forced_on; else kPlatformProvided if ECHO_CANCELLER effect; else kChromeWide if IsChromeWideEchoCancellationEnabled(); else kPeerConnection. => default true never picks loopback; 'all' does, deterministically, on Win11 / macOS 14.2+.
- services/audio/stream_factory.cc: LoopbackReferenceManager created only if IsSystemLoopbackAsAecReferenceEnabled(); input_controller.cc AECType {kNoAudioServiceAEC, kChromeWideAEC, kLoopbackAEC}.
- W3C: raw.githubusercontent.com/w3c/mediacapture-extensions/main/index.html contains no "all"/"remote-only" echoCancellation text (only one echoCancellation mention) => the string modes are a Chromium-shipped, not-yet-in-spec extension [likely; absence-based].

D. Platform (OS) AEC in Chrome desktop exists but is off by default [verified]
- kEnforceSystemEchoCancellation (Mac/Win) DISABLED_BY_DEFAULT. media/audio/apple/audio_low_latency_input.cc AUAudioInputStream::IsEchoCancellationSupported returns false unless IsSystemEchoCancellationEnforced(); otherwise uses kAudioUnitSubType_VoiceProcessingIO (mono/stereo only, not aggregate devices). media/audio/win/core_audio_util_win.cc: "The EnforceSystemEchoCancellation flag must be set to support audio effects"; AEC via IAudioEffectsManager (AUDIO_EFFECT_TYPE_ACOUSTIC_ECHO_CANCELLATION, needs build 22000+). So on default Chrome the claim's list is complete; with --enable-features=EnforceSystemEchoCancellation a VPIO/Windows-effects system AEC path also exists (and would then be what 'all' and even true select).

E. Web Speech API capture path: AEC only applies if you hand it a getUserMedia track [verified]
- content/browser/speech/speech_recognizer_impl.cc: plain recognition.start() opens the mic with audio::CreateInputDevice(stream_factory, device_id_, DeadStreamDetection::kEnabled, log) and no processing_settings (services/audio/public/cpp/device_factory.h default std::nullopt; input_ipc.cc sends null AudioProcessingConfig; input_controller.cc MaybeSetUpAudioProcessing returns early "undefined audio processing config" => AECType::kNoAudioServiceAEC). i.e. NO echo cancellation of any kind, not even Chrome-wide.
- speech_recognition.idl: start(MediaStreamTrack track) [RuntimeEnabled=MediaStreamTrackWebSpeech]; runtime_enabled_features.json5 status: Linux/Mac/Win "stable", default (incl. Android) "experimental". speech_recognition.cc attaches a WebMediaStreamAudioSink to the track (SpeechRecognitionAudioForwarder). So AEC'd recognition on desktop = getUserMedia({audio:{echoCancellation:'all'}}) + recognition.start(track).
- Android: content/public/android/.../SpeechRecognitionImpl.java uses android.speech.SpeechRecognizer.createSpeechRecognizer(ctx, provider) => the recognizer service (Google app) captures the mic; Chrome sets no audio source/AEC. Whether that service applies AEC: uncertain (no source found).
- Android getUserMedia: media/audio/android/aaudio_input.cc uses AAUDIO_USAGE_VOICE_COMMUNICATION unconditionally; audio_manager_android.cc sets ECHO_CANCELLER effect when AcousticEchoCancelerIsAvailable() => GetPreferredAec -> kPlatformProvided (and 'all' == platform AEC, not loopback). That the Android platform AEC reference includes TTS output: likely (device-level), not verified from Android docs.

F. iOS/macOS Safari [verified code; scope of VPIO likely]
- WebKit Source/WebCore/platform/mediastream/cocoa/CoreAudioCaptureUnit.cpp createAudioUnit(shouldUseVPIO): kAudioUnitSubType_VoiceProcessingIO when EC on, else kAudioUnitSubType_RemoteIO (iOS) / kAudioUnitSubType_HALOutput (Mac). With VPIO WebKit sets kAUVoiceIOProperty_OtherAudioDuckingConfiguration {advanced=true, kAUVoiceIOOtherAudioDuckingLevelMin} => the OS may duck "other non-voice audio" (which includes speechSynthesis) on local voice activity.
- WebKit SpeechRecognition on Cocoa: Modules/speech/cocoa/WebSpeechRecognizerTask.mm uses SFSpeechRecognizer + SFSpeechAudioBufferRecognitionRequest fed from WebKit's own RealtimeMediaSource created by SpeechRecognitionCaptureSource::createRealtimeMediaSource -> audioCaptureFactory().createAudioCaptureSource(device, {"SpeechID"...}, { } /*no constraints*/, page) => default EC on => VPIO. So on iOS Safari both gUM and SpeechRecognition mic input are VPIO-processed by default.
- Apple AVAudioSession.setPrefersEchoCancelledInput(_:) doc: "Audio sessions using Apple's voice processing APIs don't need this option because the system automatically applies echo cancellation to these routes" and the goal is input "clear of any echoes from the audio playing out of the built-in speaker" (route/device-level, so AVSpeechSynthesizer output is in scope) [likely: Apple does not literally say "all apps' audio"]. voiceChat mode doc: apps not using Voice I/O get no "echo cancellation and automatic gain correction".

  CORRECTION: Core claim holds; fix these details. (1) Provider: on Android 12+ (SDK S) Chromium binds `com.google.android.tts` ("Speech Services by Google"), not the Google app; AGSA (`com.google.android.googlequicksearchbox`, versionCode >= 300207030) only on Android <= 11. Either way the mic is opened by that separate process (RecognitionService), never by Chrome. (2) `continuous` is not literally ignored: Chromium forwards it as the undocumented extra `android.speech.extra.DICTATION_MODE` (absent from AOSP RecognizerIntent.java), promotes provisional results to final, and terminates the session on the provider's first `onResults`; net effect per MDN BCD "can be set, but has no effect" and user reports ("microphone constantly resets"). (3) Beep: no primary source; only user reports (2020, Nov 2023, Oct 2024: beeps on start and at every end-of-speech even in continuous mode) -> likely. (4) MODE_IN_COMMUNICATION is set only when the Chrome input stream carries an effect, i.e. ECHO_CANCELLER, which happens when `AcousticEchoCanceler.isAvailable()` AND the track's AEC is platform-provided (the default `kBrowserDecides` path picks platform AEC whenever available). `echoCancellation:false` (with NS/AGC off) yields NO_EFFECTS: no mode switch, AAudio `AAUDIO_INPUT_PRESET_GENERIC` (not privacy-sensitive; recent M153-era change with rollback flag `kForceAAudioCamcorderInputPreset`; OpenSLES fallback still uses CAMCORDER = privacy-sensitive). Mode is also not changed if another Chrome input stream already exists, and the desktop-Android `kAAudioPerStreamDeviceSelection` path (requires `is_desktop()`) skips it entirely. Input uses `AAUDIO_INPUT_PRESET_VOICE_COMMUNICATION`; `AAUDIO_USAGE_VOICE_COMMUNICATION` applies to output streams while comm mode is on. (5) Bluetooth SCO is engaged only when the BT headset is the selected communication device (pre-S `startBluetoothSco()`, S+ `setCommunicationDevice(TYPE_BLUETOOTH_SCO)`); default selection order is wired > USB > Bluetooth > speakerphone, so a connected BT headset with no wired/USB device does go to SCO. (6) Policy is stronger than "most combinations": with a default getUserMedia open, Chrome's capture is privacy-sensitive AND Chrome is the MODE_IN_COMMUNICATION owner, so AudioPolicyService silences any other uid's capture (incl. the Assistant) unless it holds CAPTURE_AUDIO_OUTPUT / BYPASS_CONCURRENT_RECORD_AUDIO_RESTRICTION (unknown for Google's recognizer). With AEC off, the "two ordinary apps" rule still favors the TOP app (Chrome) on Android 12+; on Android <= 11 the AGSA provider is the Assistant uid and could capture concurrently with a non-sensitive Chrome stream (unmeasured). Also: Chromium Android has no on-device Web Speech path (`UseOnDeviceSpeechRecognition` returns false on Android; BCD processLocally/available unsupported) and kills recognition when the page is hidden.
