# storage-sync

## Topic
Persisting and syncing one user's learning progress from a static GitHub Pages app (no backend) between a PC browser and a phone, 2026-10

## Summary
1. Local-only storage is not durable on iOS: Safari deletes all script-writable storage (localStorage, IndexedDB, Cache, SW) for an origin with no user interaction in the last 7 days of browser use; Home Screen web apps are exempt and have their own isolated storage. Chrome/Firefox only evict under disk pressure (LRU).
2. navigator.storage.persist() exists everywhere (Chrome 55, Firefox 57, Safari 15.2) but Chrome grants it only for installed/"important" sites and Safari grants it only for domains ITP already exempts from deletion (WebKit source), so it cannot be relied on; Firefox prompts.
3. api.github.com supports CORS from any origin (Access-Control-Allow-Origin: *) with an Authorization header, so a GitHub Pages app can talk to GitHub directly with a token.
4. Gists are the wrong store: fine-grained PATs expose only POST/PATCH/DELETE gist endpoints (no GET, cli/cli#7803 still open), the Gists permission is write-only, secret gists are readable by anyone with the URL, and PATCH /gists has no sha/precondition (no conflict detection).
5. A private repo via the Contents API is the right store: GET returns sha + ETag (304 is free), PUT requires sha when updating (409 Conflict on stale sha, 422 when missing), 1 MB per file for full GET, 5,000 req/h primary limit, 80 content-creating req/min and 500/h secondary limit.
6. A fine-grained PAT can be limited to one selected repository with only Contents: Read and write (plus mandatory Metadata read); expiration default 30 d, up to 366 d or none for personal accounts; GitHub auto-revokes PATs leaked in public repos.
7. Google Drive appDataFolder needs a Google Cloud OAuth client; browser tokens last 1 h with no refresh and no silent refresh; Dropbox needs an App Console app + PKCE; Nextcloud WebDAV sends no CORS headers by default. All are higher friction than a PAT for someone who already has GitHub.
8. Manual JSON export/import works on every platform (Web Share with files on iOS/Safari 14+, download elsewhere, <input type=file> to import); File System Access API is Chrome/Edge only.
9. WebCrypto AES-GCM + PBKDF2 is universally supported (Safari 11+); cost is a passphrase the user must type on each device and can lose.
10. Recommended: private repo + fine-grained PAT + append-only JSONL merged by event id with sha-based conflict retry; fallback: export/import JSON file.

## Recommendations
- Default: private GitHub repo as the sync store via the Contents API from the browser. One-time setup for the user: create an empty private repo (e.g. english-vera-data), create a fine-grained PAT with Repository access = Only select repositories (that repo), Permissions = Contents: Read and write, expiration 366 days or No expiration; paste the token into the app on each device (optionally transfer it PC->phone with a QR code rendered by the app). Store token + data in IndexedDB; use 'Authorization: Bearer', 'Accept: application/vnd.github+json', and do not send X-GitHub-Api-Version from the browser.
- Data layout: events.jsonl (append-only event log, merged by event id) plus snapshot.json derived on each device; last-writer-wins per record by (ts, id). Sync = GET with If-None-Match (304 is free) -> merge -> PUT with the sha from the GET -> on 409/422 re-GET, re-merge, retry with jitter. Debounce PUTs to at most one per ~10 s and never exceed 80 content-creating requests/min; compact the log before it reaches ~700 KB (1 MB full-GET limit).
- Local layer: write every event locally first (IndexedDB, with a localStorage mirror of the small snapshot as a cheap fallback), call navigator.storage.persist() opportunistically, show 'last synced' state, and on iOS prompt the user to Add to Home Screen (exempt from the 7-day ITP purge, own storage). Treat local data as a cache; the repo is the source of truth.
- Fallback (zero setup, offline): Export/Import JSON. Export via navigator.share({files:[File]}) when canShare supports files (iOS/Android/Safari/Chrome), else an <a download> Blob link; import via <input type=file accept='.json,application/json'>. Import uses the same id-merge logic so it never overwrites newer local progress.
- Do not use gists (fine-grained PATs cannot GET gists, secret gists are URL-public, no conflict detection), Google Drive appData (Google Cloud OAuth client setup, 1-hour tokens with no silent refresh), Dropbox (App Console setup), Nextcloud/WebDAV (no CORS by default), or the File System Access API (Chromium-only).
- Encryption at rest: optional toggle, off by default because the repo is already private. If enabled: AES-256-GCM with a key derived by PBKDF2-HMAC-SHA256 (>=600,000 iterations, 16-byte salt, 12-byte IV per write); encrypt each JSONL line or the whole file; cache the non-extractable CryptoKey in IndexedDB so the passphrase is typed once per device; warn that a lost passphrase means lost data.
- Security hygiene: no third-party scripts on the page, strict CSP (connect-src https://api.github.com), never put the token in a URL, offer a 'Forget token on this device' button, and tell the user GitHub auto-revokes PATs that leak publicly.
- Verification tasks before building: from the deployed GitHub Pages origin, run one real GET/PUT with a fine-grained PAT from Chrome desktop, Android Chrome and iOS Safari (tab and Home Screen) to confirm CORS headers and the 409 path; measure round-trip latency on mobile data.

LIKELY (secondary; GitHub does not document which condition yields 409)
- A sha that does not match the current blob -> `409 {"message":"<path> does not match <sha-you-sent>"}`: PyGithub #1815 (Jan 2021, update_file with file.sha) and go-github #2707 (Mar 2023, reporter sent a commit sha instead of blob sha) both show exactly this body. No 2025-2026 primary confirmation; GitHub's spec only lists 409 "Conflict".
- Omitting sha on an existing path -> `422 "Invalid request.\n\n\"sha\" wasn't supplied."` (PyGithub #2281, Jul 2022) — i.e. missing sha is 422, not 409.
- Branch-level race (two PUTs racing on the same branch/tree, e.g. two files in one new directory) -> `409 {"message":"is at X but expected Y"}`; also `409 "Sorry, a file exists where you're trying to create a directory"` (third-party notes dated 2026-07, handsomehu80/hermes-config). So 409 is not only "your blob sha is stale".
- Because of `Cache-Control: private, max-age=60`, a browser fetch() with default cache mode may serve a <=60 s-old cached GET (old sha) -> harmless (PUT then 409s) but costs a retry; use `cache: 'no-cache'`/`'no-store'`. HTTP caching spec (RFC 9111) and fetch spec were egress-blocked, so this is inference from the observed header.

(1) OUTDATED: since WebKit PR #21120 (merged 2024-02-09, shipped in WebKit 619-era Safari, i.e. ~Safari/iOS 17.4+; still the code on main as of 2026-10-02), the default window for deleting a first-party site's script-written storage (localStorage, IndexedDB, Cache API, SW registrations, etc.; server-set cookies excluded) is 30 "operating days" (days Safari/ITP actually ran) without user interaction (tap/click) on the site. The 7-operating-day window now applies only to domains whose DataRemovalFrequency is Short, i.e. the site was reached by a cross-site navigation carrying link decoration from an ITP-classified prevalent (tracker) domain while known-tracking-parameter filtering was NOT active. A plain GitHub Pages app opened from a bookmark/typed URL is on the 30-day schedule. A May-2025 WebKit PR (#46107) to relax this further to 400 days is still open/merging-blocked, not shipped. The deletion only runs when "Prevent cross-site tracking" (ITP) is on (Safari default). (2) CONFIRMED: Home Screen web apps: WebKit's ITP store permanently exempts the data store's standaloneApplicationDomain (set from _WKWebsiteDataStoreConfiguration.standaloneApplicationURL) together with app-bound, managed and "persisted" domains; WebKit source comment: "Domains permanently configured to be exempt. This can be home screen web applications, app-bound domains, or similar." That iOS's Home Screen web-app container actually sets standaloneApplicationURL is Apple-side and only 'likely'. (3) CONFIRMED and stricter than MDN says: navigator.storage.persist() in Safari/WebKit resolves true only if (a) top-level origin == client origin, (b) the session is persistent (not ephemeral/private), and (c) the origin's registrable domain is in NetworkProcess::registrableDomainsExemptFromWebsiteDataDeletion = appBoundDomains ∪ managedDomains ∪ persistedDomains (_WKWebsiteDataStore._persistedSites SPI, iOS 18.2/macOS 15.2+, set by the embedding app) ∪ standaloneApplicationDomain. There is NO interaction-history heuristic (MDN's "based on the user's history of interaction" is inaccurate for Safari); an ordinary site in Safari gets false. If ITP is disabled the exempt set is empty and persist() also returns false. (4) CONFIRMED for Chrome: PersistentStoragePermissionContext::DecidePermission grants (no prompt) only when the request is top-level, cookies are not session-only/blocked, and the registrable domain is either an installed web app (ImportantSitesUtil::GetInstalledRegisterableDomains) or among the top-10 "important sites" (site engagement >= MEDIUM, notifications permission ALLOW, prior persistent-storage ALLOW, or bookmarked); otherwise the promise resolves false (PermissionDecision::kNone). Architectural consequence still holds: on iPhone Safari (non-installed) local storage is best-effort and will be wiped after 30 operating days of no interaction (7 in the tracker-link-decoration case), so a repo/cloud copy or export remains mandatory; the "token re-entry" risk is 30-day-of-use, not 7-day.
